# 网页系统自动化测试

三层，从浅到深：
1. **菜单巡检**：自动找出所有菜单，逐个点开，看页面和页面调的接口有没有出错。不用写用例。
2. **接口检查**：页面实际调到的接口自动汇总成清单；有接口文档的，查询类接口逐个调一遍；再写接口用例测规则。
3. **功能逻辑**：把业务规则写成用例（接口用例、页面用例），一条条验证。

工具只管「执行和判断」；**哪些规则要测、期望结果是什么，是你要想清楚写进用例的**——这是这个技能最值钱的部分，见第 4 节。

## 0. 第一次用：装依赖

```bash
cd <本技能目录> && npm install && npx playwright install chromium
```
- 要 Node 18 以上。浏览器下载慢：先设 `PLAYWRIGHT_DOWNLOAD_HOST=https://registry.npmmirror.com/-/binary/playwright` 再装；或不下，在配置里写 `browser: { channel: chrome }` 用本机 Chrome。
- 跑一下 `npm run demo` 确认装好：会起一个故意埋了 6 处问题的演示后台并测一遍，报告里应查出这 6 处。

## 1. 先问清楚（缺哪个问哪个，一次问完）

- 被测系统网址；是**测试环境**还是线上（线上只跑菜单巡检和查询类接口，不跑会改数据的用例）。
- 测试账号怎么给：让用户设环境变量 `TEST_USER`、`TEST_PASSWORD`，**不要把密码写进文件**。登录有验证码的，请对方在测试环境关掉或给万能码。
- 有没有接口文档地址（Swagger / Knife4j / OpenAPI，常见 `/v3/api-docs`、`/v2/api-docs`、`/doc.html` 背后的 json）。
- 有没有前后端源码、需求文档：有就读，用例从这里来。

## 2. 搭起来，先跑菜单巡检

```bash
node <本技能目录>/scripts/autotest.js init autotest          # 在项目里生成 autotest/测试配置.yaml 和用例模板
# 改 autotest/测试配置.yaml：baseUrl、login、api.business、menus.start
node <本技能目录>/scripts/autotest.js run autotest/测试配置.yaml --only menus
```

配置要点（全部写法见 `references/写法.md`）：
- **登录**：优先 `login.steps` 在登录页填表（最像真人）；前端令牌放 localStorage 的，用 `login.api` 拿令牌 + `login.localStorage` 塞进去更快。先看前端源码里登录后把令牌存在哪个键、什么格式，照样写。
- **业务错误码 `api.business`**：先看一个接口返回长什么样。出错也回 200、靠 `code` 区分的（国内后台大多如此），**必须写**，否则查不出业务错误。若依、pig 一类 `ok: [0, 200]`。
- **菜单认不出**：跑完看报告目录 `shots/没找到菜单.png`。没登录上就修 login；顶部菜单、折叠菜单、菜单在 iframe 里的，改 `menus.source: api`（从菜单接口取路由）或 `menus.list`。
- 第一次跑先 `menus.limit: 3` 试通，再放开。

跑完读报告目录里的 `results.json`：
- `menus.items`：找到了哪些菜单、每个的网址、问题、调到的接口。**核对菜单数和系统里看到的一致**，少了就是找菜单的配置不对。
- `apis`：页面实际调到的所有接口（同一路径不同 id 已合并成 `{id}`），带状态码、最慢耗时、返回样例 `sample`。写接口用例时照这里的真实路径和返回结构写。

## 3. 接口检查

- 有接口文档：配 `api.openapi`，默认只调 GET。路径里有 `{id}` 的要在 `params` 给一个真实存在的值，否则记「跳过」。要测写接口，在 `bodies` 里按接口给请求体（只在测试环境）。
- 「页面调到的接口」清单是自动的：菜单巡检和页面用例过程中每个接口的状态都在里面。
- 页面上没调到、文档里也没有的接口，写接口用例补。

## 4. 功能逻辑：怎么想用例

按模块（一般一个菜单一个模块）读需求、前端页面、后端接口代码，把**规则**列出来，每条规则一个用例或一组数据。常见的几类，逐类过一遍：

| 类别 | 要测什么 | 怎么判断 |
|---|---|---|
| 增删改查闭环 | 新增后能查到、字段和提交的一致；改了生效；删了查不到 | 接口用例前一步 `save`，后一步查回来比 |
| 校验 | 必填、格式（手机、邮箱、身份证）、长度、重复（唯一）、数值范围 | `each` 列出各种坏数据，期望被拒（`$.code: {ne: 0}` 或具体提示语） |
| 查询筛选 | 按每个条件筛，结果**每一条**都符合；组合条件；关键字模糊 | `{ every: { 字段: 期望 } }` |
| 排序分页 | 排序方向对；翻页不重不漏；total 和实际条数一致 | `{ sorted: desc }`、两页 id 不重叠 |
| 计算 | 合计、金额、数量、统计数字和明细对得上 | 先取明细自己算（`js` 步骤或多次 `save`），再和汇总比 |
| 状态流转 | 只能按规定顺序变（待审→已审→已完成），不能跳、不能回退 | 走一遍正常流程；再试非法流转，期望被拒 |
| 权限 | 不带令牌 401；没权限的账号看不到菜单、调接口被拒；只能看自己的数据 | 第二个账号另写一份配置跑，或接口用例里换 headers |
| 关联 | 删了被引用的数据（如有用户的角色）要被拦，或级联处理 | 期望被拒或关联数据同步变 |
| 页面与接口一致 | 页面显示的和接口返回的一致；点按钮真的调了对的接口 | 页面步骤加 `response:`，再 `expectText` |

写法原则：
- **一个用例只测一条规则**，名字直接写规则（「按状态筛选，结果全是这个状态」），失败时一看名字就知道哪条规则坏了。
- 期望值**从需求和代码里来**，不从「系统现在返回什么」抄。抄当前返回只能防回退，测不出本来就错的逻辑。
- 测试数据名字用 `autotest_${rand}` 开头，**写数据的用例一定写 `cleanup`** 删掉。
- 先用接口用例把规则测透（快、稳），页面用例只做主流程（新增、搜索、删除各走一遍），别把每条规则都做成点页面。
- 每写完一个文件先 `check` 再 `run --grep 名字` 单独跑通，再写下一个。

## 5. 跑和看结果

```bash
node <本技能目录>/scripts/autotest.js run autotest/测试配置.yaml            # 全跑
node <本技能目录>/scripts/autotest.js run autotest/测试配置.yaml --grep 用户  # 只跑相关的
node <本技能目录>/scripts/autotest.js run autotest/测试配置.yaml --headed     # 弹出浏览器看着跑（本机有界面时）
```

用例失败时先分清是**系统的错还是用例的错**：
- 看报告里失败那步的说明、返回内容和截图。选择器找不到、等超时、变量没取到，多半是用例写错，改用例。
- 返回内容和规则对不上，就是系统的问题，**不许为了变绿去改期望值或删用例**。拿不准的，在给用户的结论里写清「按需求应该是 X，实际是 Y，请确认规则」。
- 偶尔失败的（网络抖、加载慢）调 `timeout` 或加 `wait`，别加长到掩盖真慢的问题。

## 6. 交给用户

只交结论：
- 一句话总数：菜单 N 个 X 个有问题，接口 N 个 X 个出错，功能用例 N 个 X 个没通过。
- 要修的问题逐条：在哪（菜单路径 / 接口 / 用例名）、现象、哪个规则被违反；报告里的「要修的问题」表就是这个清单。
- 附上报告目录（report.html + shots），告诉对方用浏览器打开 report.html。
- 用例文件留在项目的 autotest 目录里，以后每次改完代码跑一遍就是回归测试；可以放进流水线（退出码非 0 即有问题，`junit.xml` 给流水线显示）。

## 注意

- 菜单巡检只点菜单，不点页面里的按钮，不会改数据；但被测系统打开页面就写数据的（如自动签到、记访问），心里有数。
- 接口文档逐个调默认只调 GET。导出、下载、发短信这类 GET 接口用 `exclude` 排掉。
- 浏览器确认框默认点「确定」，删除类页面用例要在测试环境跑。
- 跑线上环境：`--only menus` 加上不写数据的接口用例，别跑带新增删除的用例。
