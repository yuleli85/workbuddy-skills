# 代码审计

工具只做两件事：**把项目摸清（底稿）**和**把结论排成正式报告**。中间的审计——对需求、找 bug、判断漏洞能不能利用、实现合不合理、照手册装一遍——是你要做的，这是这个技能最值钱的部分。

自动扫描的每一条都只是**疑点**，必须逐条看代码判断属实、误报还是可接受；不许不看就整批判误报，也不许为了报告好看改级别。

## 0. 工具

```bash
python <本技能目录>/scripts/audit.py scan   <项目目录> [-o 输出目录]   # 扫描，出底稿和结论模板
python <本技能目录>/scripts/audit.py check  <输出目录>                # 查结论写全没有
python <本技能目录>/scripts/audit.py report <输出目录>                # 出报告（HTML + Markdown）
python <本技能目录>/scripts/audit.py demo                             # 自检：演示项目埋了问题，应全部查出
```
- 只要 Python 3.8+，不用装依赖。Windows 用 `python`，Mac/Linux 用 `python3`。
- 输出目录默认是 `<项目>/审计结果`；不想写进项目就用 `-o` 指到别处。
- `scan` 的选项：`--since <版本>` 只查这个版本之后改过的文件（审一次改动）；`--exclude 目录 ...` 跳过目录；`--no-tools` 不调外部工具；`--online` 允许联网检查（npm audit）。
- 本机装了 gitleaks 会自动用它查密钥，有 `.git` 时连提交历史一起查。
- `report --fail-on 高` 有高及以上问题时退出码为 1，可放进流水线。

**大仓库（10 万行以上）先排除非项目代码，否则疑点数会被撑爆**：技能目录（`.claude/skills`、`.github/skills`、`.workbuddy/skills`）、构建产物（`output`、`dist`、`release`）、生成的文档站、快照备份等会被当成业务代码扫进来（实测一个 84 万行仓库因此多出 20% 噪声，且同一份脚本在三处技能目录里各算一遍）。建议：

```bash
python scripts/audit.py scan . -o <输出目录> \
  --exclude output dist .claude .github .workbuddy node_modules
```

排除前先确认这些目录不属于交付物；被排除的目录要在报告的 `scope` 里写明「未纳入」，不要让报告看起来审了全部。

## 1. 先问清楚（缺哪个问哪个，一次问完）

- **代码在哪**：本地目录或仓库地址；审哪个分支、哪个版本；审全部还是只审某次改动。
- **对照什么**：需求说明、合同里的功能清单、设计文档、接口文档。没有就说明「按代码和文档推断功能」，写进 `basis`。
- **审计目的**：验收（外包交付）、上线前检查、日常审查。决定报告的措辞和建议结论。
- **交付物清单**：合同或约定里要交哪些（源码、脚本、用户使用手册、部署手册、接口文档、测试报告、数据库脚本、版本说明……）。没约定就按 `references/交付物清单.md` 的通行清单查。
- **能不能跑**：有没有可以装起来的环境、测试数据库、测试账号。能跑一定要跑——跑出来的结论比读代码可靠。
- 报告给谁看：给客户、给供应商、给内部。决定写多细、要不要隐去内部信息。

## 2. 扫描，读底稿

```bash
python scripts/audit.py scan <项目目录> -o <输出目录>
```
读 `<输出目录>/审计底稿.md`：项目概况（语言、框架、依赖、测试、建议的构建命令）、交付物自动判断、配置一致性、自动扫描疑点（按规则分组，带编号、位置、代码片段）、组件漏洞、重复和超长代码、外部工具结果。底稿只给审计的人看，不交给客户。

大项目（几十万行）：先看底稿的规模和框架，按模块分批审，优先**登录和权限、钱和数量的计算、文件上传下载、对外接口、导入导出、定时任务**这几块。

## 3. 人工审计（按维度，逐项做）

细项清单在 `references/审计清单.md`（按维度和技术栈分），下面是主线：

1. **跑起来**：照 README 或部署手册装依赖、构建、跑测试、启动。装不起来本身就是问题（交付物或部署问题）。把结果写进 `checks`。
2. **功能是否实现**：需求逐条找到实现代码（接口、页面、表），判断已实现 / 部分实现 / 未实现 / 与需求不一致 / 无法判断；能跑的挑核心规则实测（边界值、状态流转、权限）。每条写清在哪、差什么。
3. **bug**：读核心流程的代码，重点看边界条件（大于还是大于等于、空值、空列表、0）、金额和数量计算、状态流转、并发和重复提交、事务、异常是否被吞掉、资源释放、时区和日期。
4. **安全**：越权（查改别人的数据，这是扫描查不出、最常见的严重问题）、未登录可访问的接口、注入（SQL、命令、表达式）、上传、反序列化、密钥和口令、加密和口令存储、跨站脚本、跳转和服务端请求、调试接口、日志里的敏感信息。扫描疑点逐条判断能不能被外部利用。
5. **合理性**：分层是否清楚、重复代码、超长函数、写死的地址和配置、数据库设计（索引、金额类型、字段长度）、查询性能（循环里查库、一次查全表）、日志和错误处理是否统一。只提真影响维护或性能的，不挑代码风格的刺。
6. **交付物**：对照清单逐个打开看内容，不只看有没有这个文件。部署手册要能照着装起来；用户手册要覆盖全部功能；接口文档要和代码一致；配置项要在手册里写全（底稿「配置一致性」列了代码读了但文档没写的配置项）。
7. **依赖和许可**：底稿列了有已知漏洞的组件版本，核实是否真用到有漏洞的功能；版本「待核」的去锁文件或构建结果里查实际版本。商用项目注意 GPL / AGPL 类许可。机器上有 pip-audit、osv-scanner、npm audit、semgrep 的可以加跑，结果一并核对。
8. **合规**：个人信息（手机号、身份证、地址）有没有加密存储、脱敏展示、日志里有没有打出来；有没有超范围收集。
9. **运维**：启动停止脚本、容器配置、数据库升级脚本、备份、健康检查、日志位置、监控。脚本里的危险命令（删除用变量、放开权限、下载即执行）。
10. **测试**：有没有自动化测试、能不能跑通、覆盖了核心规则没有。

## 4. 核对扫描疑点

每条疑点在 `审计结论.json` 的 `autoReview` 里给结论（写法见 `references/结论写法.md`）：
- **属实**：确实是问题。同一规则的属实疑点会自动合并成一个问题进报告；属于你已写好的某个问题的，用 `issue` 挂上去，位置自动并入。
- **误报**：其实不是问题（例如变量名叫 password 但值来自环境变量）。写理由。
- **可接受**：是这种写法但这里不构成风险（例如测试代码、一次性迁移脚本）。写理由。

可以按规则整批判（同一规则的都一样时），也可以按「规则 + 目录」（例如工具脚本目录下的都可接受），个别不同的用编号单独判。整批判之前抽看几条确认真是一样的。

## 5. 写结论，出报告

1. 在 `审计结论.json` 里写：`summary`（总体结论，3~5 句，先说能不能验收，再说最要紧的几个问题）、`requirements`、`issues`（人工审出的问题）、`autoReview`、`deliverables`、`checks`。
2. 级别按影响定：
   - **严重**：可被直接利用造成数据泄露、篡改或服务被控制；核心功能不能用；金额算错。必须修。
   - **高**：特定条件下出错或被利用；影响主要功能。验收前修。
   - **中**：影响局部功能或体验；有隐患但利用难。限期修。
   - **低**：规范和可维护性问题。排期修。
   - **建议**：改进意见。
3. 每个问题写清：在哪（文件:行）、现象（实测结果优先）、影响（用业务的话说后果）、怎么改（具体到做法）。
4. `python scripts/audit.py check <输出目录>`，把错误和提醒都处理掉（还有没核对的疑点、部分实现的需求没对应问题、交付物还是待核，都会提醒）。
5. `python scripts/audit.py report <输出目录>`，出 `审计报告.html`（浏览器打开、可直接打印成 PDF）和 `审计报告.md`（`pandoc 审计报告.md -o 审计报告.docx` 转 Word）。`verdict` 不填就按问题级别给建议结论。
6. 打开报告从头看一遍：能不能原样交给对方；内部的话、真实口令（扫描到的代码片段已自动打码，你自己写的问题描述要自己注意）、无关的过程不要出现。

## 6. 交付

- 给用户的：报告（HTML 或转好的 PDF / Word）+ 一段话结论（能不能验收、几个严重和高级别问题、最要紧的两三条）。
- 底稿和 `scan.json` 留在输出目录备查，不发给对方。
- 复审：对方改完后在同一个输出目录重新 `scan`（`审计结论.json` 不会被覆盖），逐个问题复核，已修好的从 `issues` 去掉或在 `detail` 里注明复核结果，再出报告。

## 不要做的

- 不改被审的代码（除非用户明确要你修）；审计只出结论。
- 不在报告里贴真实口令、密钥、个人信息。
- 不为了「通过」改需求、改级别、整批判误报。
- 扫描没报的不代表没问题：越权、业务逻辑错、需求没做，只能靠人工审。
