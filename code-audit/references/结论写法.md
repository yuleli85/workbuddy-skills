# 审计结论.json 写法

`scan` 第一次运行时在输出目录生成模板（已有就不覆盖）。完整示例见 `examples/演示项目-审计结论.json`；空白模板见 `templates/审计结论.json`。

## 顶层字段

| 字段 | 必填 | 说明 |
|---|---|---|
| project | 是 | 项目名称，进报告标题 |
| version | | 审计的版本（版本号或提交编号） |
| purpose | 是 | `验收` / `上线` / `审查`，决定建议结论的说法（不建议验收 / 不建议上线 / 不建议合入） |
| scope | | 审计范围，例如「后端全部源码、前端管理端、数据库脚本和随附文档」 |
| date | | 审计日期 |
| auditor | | 审计人或单位，不写就不显示 |
| basis | | 审计依据，数组，例如 `["《XX 需求说明》v1.2", "合同附件二 交付物清单"]` |
| summary | 是 | 总体结论 3~5 句：能不能验收；最要紧的几个问题；需求和交付物的总体情况；下一步建议 |
| verdict | | 结论标题。不填就按问题级别自动给（有严重 → 不建议验收；有高 → 修完高级别问题后再验收；有中 → 可以验收，其余问题限期整改；否则 → 可以验收） |
| requirements | | 需求对照，见下 |
| issues | | 人工审出的问题，见下 |
| autoReview | | 扫描疑点的核对结论，见下 |
| deliverables | | 交付物检查，见下 |
| checks | | 运行验证，见下 |

## requirements：需求对照

```json
{"id": "R3", "text": "满 100 元（含 100 元）减 10 元", "status": "与需求不一致",
 "where": "services/order.py calc_total", "note": "写成了大于 100 才减；实测 50 元×2 件结果为 100.0"}
```
- status：`已实现` / `部分实现` / `未实现` / `与需求不一致` / `无法判断`
- 不是「已实现」的，问题清单里要有一个问题用 `"req": "R3"` 对上（`check` 会提醒）。

## issues：问题

```json
{"id": "M02", "dim": "缺陷", "level": "高", "title": "满减算错：正好 100 元的订单没有减 10 元", "req": "R3",
 "where": ["services/order.py:12"],
 "detail": "条件写成 total > 100，需求是满 100（含 100）。",
 "impact": "所有正好 100 元的订单多收 10 元，会引发客诉。",
 "fix": "改成 >= 100，并补 99.99 / 100 / 100.01 三个边界的测试。"}
```
- id：自己编号（建议 M01 起）。不写的自动编 A01 起。
- dim：`功能` / `缺陷` / `安全` / `合理性` / `交付物` / `依赖` / `合规` / `运维` / `测试` / `规范`
- level：`严重` / `高` / `中` / `低` / `建议`（定义见 SKILL.md 第 5 节）
- where：数组，`文件:行`；不对应具体文件的写 `["整个项目"]`。
- title 一句话说清是什么问题；detail 写现象（实测结果优先）；impact 用业务的话说后果；fix 写具体做法。

## autoReview：扫描疑点核对

每条扫描疑点都要被某一条核对结论匹配上，否则算「待核」（`check` 会提醒，报告里也会写出待核数）。

匹配方式（越具体越优先：`id` > `ids` > `rule + path` > `rule`）：

```json
{"rule": "SEC-SQL-CONCAT", "verdict": "属实", "reason": "..."}                      // 这条规则的全部疑点
{"rule": "SEC-SQL-CONCAT", "path": "tools/", "verdict": "可接受", "reason": "一次性迁移脚本，不对外"}  // 这条规则在某目录下的
{"id": "S-3fa2c1", "verdict": "误报", "reason": "值来自环境变量"}                    // 单条（编号见底稿）
{"ids": ["S-3fa2c1", "S-9b07e4"], "verdict": "属实", "issue": "M05"}                // 几条
```

- verdict：`属实` / `误报` / `可接受`；误报和可接受要写 `reason`。
- 属实的：
  - 写 `"issue": "M05"`：并进你写的问题 M05，位置自动加进它的 where。
  - 不写 issue：同一规则的属实疑点自动合并成一个问题（编号 A01 起），标题和改法用规则自带的；可以加 `reason`（作为现象）、`impact`、`fix`、`req`、`level`（改级别，要有理由）。
- 模板里已按规则列好，并写了每条规则的疑点数（`count`，只是提示，不参与匹配）。

## deliverables：交付物

```json
{"item": "部署手册", "status": "不全", "note": "缺配置项说明、升级回滚、备份"}
```
- status：`齐全` / `不全` / `缺失` / `不适用` / `待核`
- 模板按扫描结果预填，必须人工打开看过再改；还是「待核」的 `check` 会提醒。
- 可以加合同约定的其他交付物（培训材料、安装包等）。

## checks：运行验证

```json
{"item": "按部署手册在干净环境装起来", "result": "不通过", "note": "手册没写要先建库，启动报表不存在"}
```
- result：`通过` / `部分通过` / `不通过` / `未做`
- 「未做」的在 note 里写原因（没有环境、没有测试等）。
