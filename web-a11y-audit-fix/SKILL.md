# 全站 UI 可读性审计与修复

把「帮我看看这站有什么 UI 问题」变成「**有基线、有归因、有复验、误报已校准**的闭环交付」。

核心原则：**先建立可复算的基线，再动手改；改完必须用同一把尺子复验，且要说清哪些"问题"是刻意不修的。**
没有基线就没有"修好了"，只有"我觉得好了"。

## 何时用

- 用户给一个 URL（+ 账号）要求「深度分析 UI 问题」「逐个修复直到完成」
- 全站对比度 / 无障碍（WCAG AA）排查
- 需要清扫渲染异常（`NaN%` / `undefined` / `[object Object]` / 坏图 / 空白页）
- 前端改完要证明「没有回归」

## 交付物（缺一不可）

1. **审计探针脚本**（可复跑，含环境变量开关）
2. **基线数据**（修复前的 JSONL/JSON）
3. **复验数据**（同一脚本再跑一次）
4. **一份 HTML 报告**：修复前后对照表 + 按根因归类的修复说明 + 残留项 + **豁免/误报清单**
5. **改动文件清单**（路径 + 一句话说明改了什么）

## 阶段 0：先摸清渲染链路（不做这步会白改）

**关键问题：这个 URL 背后是 dev server 还是构建产物？**

- 如果是 **nginx/静态容器托管构建产物** ⇒ **改源码不会生效**，必须 rebuild 镜像 + `--force-recreate`。
  验证方法：改一个只影响可见样式的值，rebuild 后在容器里 `grep` 构建产物确认规则进去了。
  ```bash
  docker run --rm --entrypoint sh <image> -c "grep -o 'your-selector{[^}]*}' /data/assets/*.css | head"
  ```
  再在真实浏览器里读 `getComputedStyle` 确认。
- 🔴 **镜像拉不到基础镜像时，先别改架构**。若 Dockerfile 用 `ARG REGISTRY=<镜像源>/` 拼 `FROM`，
  而本地其实**已有**该基础镜像（只是换了源的域名），把本地镜像**按 Dockerfile 期望的引用名打标签**即可：
  ```bash
  docker tag <本地镜像:tag> <REGISTRY>/<image>:<tag>     # 例：docker.m.daocloud.io/library/node:22-alpine
  ```
  精确匹配的本地引用会让 BuildKit 从**本地镜像库**解析 `FROM`，不再请求网络 metadata ⇒ 构建秒过、Dockerfile 零改动。
  ⚠️ `load metadata ... DeadlineExceeded` **不等于源不可用**，可能只是极慢（实测同一拉取 4h38m 后成功）⇒
  长拉挂后台等通知，别据此得出「源挂了 → 必须走离线路径」的结论。
- 顺带确认端口映射 **和你以为的一致**：`docker port <container>`。重建容器时带错 env 文件会静默换端口（踩过：某 Mac 覆盖文件把 8888 改成 8891，页面直接连不上）。

## 阶段 1：路由枚举 + 全站探针

**别手工列页面。** 从后端菜单接口取叶子路由（SPA 常用 `/admin/menu`），得到权威清单。

探针（Playwright）逐页采集：

| 采集项 | 判据 |
|---|---|
| console error / pageerror / unhandledrejection | 三类**都要监听**，缺一个就漏 |
| HTTP ≥ 400 | |
| 横向溢出 | 元素 `scrollWidth - clientWidth > 8` 且 `overflow-x: visible` |
| 小字 | `< 11px` |
| **对比度** | DOM 计算 + **像素回退**（见下） |
| 脏文本 | `NaN` / `undefined` / `[object Object]` / `Infinity` |
| 坏图 | `img.complete && naturalWidth === 0` |
| 空白/错误页 | 主内容区文本长度 + 错误文案正则 |
| 截图 | 便于人工复核误报 |

### 🔴 探针必须遵守的 7 条判据纪律

1. **每页先 `about:blank` 再 goto。** SPA 只切 hash 不触发重载，否则你测到的是**上一页的 DOM**。
2. **对比度必须有像素回退。** 背景含渐变/图片时 `getComputedStyle` 取不到真底色。
   取背景色**不能用众数** —— 渐变与抗锯齿会让众数退化成边缘色（实测把 `#225ddc` 取成 `#dbeafe`）。
   用「**偏暗的 40% 分位中位数**」。
3. **禁用态独立记账，不混进缺陷数。** 沿自身及最近 4 层祖先查
   `disabled` / `aria-disabled="true"` / `.is-disabled` / `cursor: not-allowed`，
   命中记到单独的 `contrastDisabled` 桶。理由：WCAG 1.4.3 明确豁免失效控件，
   而且**把禁用态文字调深会让它看起来可点**，是比对比度更严重的可用性错误。
4. **文本进度的正则要够窄。** 「无权限|没有权限」会命中空状态文案
   **「还没有权限变更留痕。」** ⇒ 把正常空列表页判成错误页。
   用 `/(^|\s)404(\s|$)|页面不存在|您没有权限访问/`。
5. **长跑探针 JSONL 增量落盘 + 支持 `START/END/ONLY`**，方便只重跑受影响页。
   ⚠️ `ONLY` 若实现成 `String.includes()` 就**不是正则** —— 传 `"a|b"` 会匹配 0 条，静默跑空。
6. **交互层必须另跑一轮 `--click`。** 弹层 / 抽屉 / 折叠展开态在静态 DOM 里**根本不存在**，
   不开就是整块漏检（实测：市场页弹层里的「下一步」「✕」两处真缺陷，静态探针一条都没报）。
   元素级复核工具也要支持 `--click`，否则展不开就取不到。
7. **复验只认运行环境实测值。** 「grep 构建产物里有没有新色值」不是证据 ——
   它只证明文件改了，不证明页面上生效。要读**浏览器计算样式**、**元素像素**或 **canvas 绘制记录**。

### 🔴 三个测量陷阱（每一个都会给出反向结论）

| 陷阱 | 错误做法会得到 | 正确做法 |
|---|---|---|
| **半透明文字不合成** | 直接拿 `rgba(15,23,42,.55)` 的字面 rgb 去算 ⇒ **3.91:1 报成 16.62:1**（虚高 4 倍） | 先 `eff = a*fg + (1-a)*bg` 再算；元素自身 `opacity` 一并乘进 `a` |
| **用 `scrollWidth` 量文本宽** | 块级 `.cell` 不换行时 `scrollWidth === clientWidth` ⇒ **恒报「装得下」** | 用 `Range` + `getClientRects()` 量文本真实宽度：`max(right) - min(left)` |
| **把容器裁剪当成单元格截断** | 以为加列宽就能修好 ⇒ 改完截图**一模一样** | 先 dump 祖先链，找 `scrollWidth > clientWidth` 的那一层：<br>· 是 `.cell` ⇒ 加列宽<br>· 是外层滚动容器 ⇒ 缩列/合并列/列固定，属**布局**决策不是对比度问题 |

**配套判据：**
- 列宽够不够，算 `可用宽 = 列宽 − 2×内边距` 再和文本实宽比（Element Plus `.cell` 内边距
  `--small` 8px / `--default` 12px / `--large` 16px，**与列宽无关**，可当常数用）。
- 「宽表要横向滚动」在多视口下结论会反转：**同一张 14 列表，1920 视口列合计 1638px = 容器 1638px 完全放得下，
  1600 视口容器只有 1318px 才需要滚动**。下结论前至少跑 1920 / 1600 / 1440 三档，别拿一个视口当普适真理。


### 校准：这些不是缺陷（先想清楚再"修"）

- 空列表页主内容文本少 ⇒ 它渲染的是「无数据~」空状态，正常。
- `el-table-fixed-column--left` 类固定列的 ~10px 溢出 ⇒ 组件库内部结构。
- 隐藏路由（菜单 `visible='0'`）直接访问报「缺少 id」⇒ 正常入口都带参数，设计如此。
- 顶栏/面包屑/侧边菜单的白字被判 1.05 ⇒ 背景是渐变，DOM 取不到；像素复核通常合格。
- **像素也采不到样（`no-sample`）⇒ 不等于缺陷。** 元素在**内部滚动容器**里时，
  文档坐标可能远超整页截图高度（实测 `y≈1086`）⇒ 必须改用 `locator.screenshot()` 元素级截图补测，
  不能把「采不到」并入「不合格」。
- **宽表横向滚动 ⇒ 通常是设计行为不是缺陷**（Element Plus `el-table--scrollable-x`）。
  下结论前先多视口实测，并区分「单元格装不下」与「容器视口裁掉」——后者要产品决策（缩列/合列/列固定）。
- **echarts 会画不可见的 `#ffffff` 遮罩文字**（与可见的 `#333333` 数字同位置各画一次）⇒
  先在 canvas 文字记录里看样本文本，再决定是不是真缺陷。
- **残留的浅色值可能是图形而非文字**（折线 série 颜色 / 进度条背景）。文字按 4.5:1，
  非文本图形按 WCAG 1.4.11 的 3:1 —— 判定口径不同，别一律当缺陷改掉。

## 阶段 1.5：多端 / 多宿主页覆盖（同源 ≠ 同观感）

**这是最容易给出错误结论的一步。** 同一份源码常被部署成多个前端（PC 站 / 桌面端 / 移动端），
同一个共享组件也常被多条路由复用。任一种情况下：

> **「某页在 A 端 0 失败」不能推出「B 端也 0 失败」。**

### 三种会让结论反向的情形

| 情形 | 表现 | 判据 |
|---|---|---|
| **共享文件只在一端被 import** | 一端复现几百条，另一端完全干净 | 比对两端入口文件（`main.ts`）的 import 列表 |
| **共享组件的宿主页不在路由清单里** | 一端报错、另一端「零失败」—— 其实是**零覆盖** | 枚举该组件的全部引用点，逐个看有没有菜单入口；不在清单里的要单独跑 |
| **同一条路由两端是不同页面** | 同名路由，DOM 文本量差 6 倍（实测 789 vs 4986） | `git log -1 --format='%h %ad %s' -- <该端该文件>`，**比提交、别比文件大小或 mtime** |

⚠️ 第 2 种最隐蔽：**某端「达标」可能只是因为那页根本没渲染出内容**。
实测一轮 13 条路由里，B 端该组件的宿主页全被注释掉了（菜单 SQL 里是注释行），
于是 B 端对这个共享组件**一次都没渲染过**，扫描结果自然是 0。

### 实操纪律

1. **枚举宿主页**：`grep -rn "<ComponentName" src/` 找出全部引用点，确认哪些在菜单树里有入口。
2. **两端各跑一遍完整清单**：探针只换 `--base`，其余参数保持不变。
3. **补一轮「隐藏宿主页」扫描**：宿主路由当前不在菜单树（被注释 / 停用）时，
   用 `--urls "/path|名称,..."` 显式指定。
4. **三者互相印证**：`textLen` / `counts.scanned` / 截图。
   - 三者矛盾时，先怀疑「两端不是同一个页面」或「扫描早于渲染」，别急着下「某端更好」的结论；
   - 若两端截图**逐字节相同**但文本量差很多 ⇒ 几乎可以确定是**不同实现**，不是渲染时序问题。
5. **共用样式文件的双端一致性纪律**：文件头写明「两端必须逐字节一致」，改一端后立刻 `cp` 到另一端
   并**校验 md5**，同时确认两端入口文件的 import **顺序也一致**
   （顺序不同会改变同特异性规则里最后胜出者）。
6. **该端专有的问题，修在该端专有的主题文件里。** 别为了「文件一致」去改另一端的共用文件 ——
   例：浅色顶栏上「令牌已淡 × 元素 `opacity` 再淡」会叠乘失效，深底白字那端本来就达标，
   一起改反而让分隔符比正文还亮。
7. **全局改动必须补跨模块回归抽样**：动了全站共用样式（token / 兜底表）后，
   除业务模块外再挑 8~16 条**其他模块**的路由跑一轮，用 `--urls` 指定即可。
   本轮就是这样抓到 3 处 info 型 `el-tag`（属于同一根因族，但不在原定范围内）。

### 🔴 测量工具自身的缺陷（比页面缺陷更危险：把合格报成不合格）

复验时若出现「明明改对了却仍不合格」，**先验证尺子，再怀疑页面**。实测踩过两个：

| 缺陷 | 症状 | 修法 |
|---|---|---|
| **颜色只解析 `rgb()/rgba()`** | 传 `#a8323f` 时解析失败、**静默回落成白色** ⇒ 「红字 on 白底」被算成「白字 on 白底」，比值 1.0–1.2 假报不合格 | `parse()` 支持 `#rgb/#rgba/#rrggbb/#rrggbbaa`；**并优先取 `getComputedStyle` 的计算色**（永远输出 `rgb()` 形式），命令行传色只作兜底 |
| **极小元素的底色取到抗锯齿中间色** | 5×14px 的「/」分隔符，真实 4.86:1 被算成 4.10 | 有效样本 < 300 像素时改用**最亮像素**作底色，并在输出里标注所用规则，便于人工复核 |
| 🔴 **切换主题后等待太短，采到 `transition: color` 的过渡中间值** | 深色注入后等 400ms ⇒ `.mob-navbar__title` 的 computed 是 `rgb(159,164,171)`（浅色 `#e8ebee` 与深底 `#1a2531` 的 0.65 中间值），1500ms 才回到 `rgb(232,235,238)`。后果：**虚增缺陷 + 每轮随机不可比**（被它误导出「基线 0 / 修复后 74」的假回归） | 深色注入后 `waitForTimeout(1500)`；**凡 before/after 对比先确认两轮等待时间一致**。含 `transition` 越多的页越要留足 |
| 🔴 **像素采样系统性低估对比度 40~50%** | `fg` 是「排除近文字色像素后取偏暗 40% 分位」⇒ `#94a3b8` 理论 6.36 只采样出 4.36 | 修值按「**采样值 ≥4.5**」而非「理论值 ≥4.5」定档，留足余量；关键处再用元素级像素复核工具二次确认 |
| 🔴🔴 **向上取背景色时「半透明 ⊕ 半透明」不累积 alpha** | 合成函数把结果一律写成 `a: 1`，于是 `if (bg.a >= 0.99) break;` **提前退出**，永远到不了真正不透明的祖先。**既造假失败又掩盖真缺陷的量级**：`rgba(239,68,68,.15) ⊕ rgba(239,68,68,.04)` ⇒ 假底 `#ef4444`（真 ≈`#3e272f`），假 3.08 / **真 11.3**；`rgba(239,243,244,.1) ⊕ rgba(29,155,240,.1)` ⇒ 假底 `[50,164,240]`（真 `[51,70,86]`），假 1.11 / **真 3.98** | 合成用标准 source-over **累积 alpha**：`a = fg.a + bg.a*(1-fg.a)`，颜色按 premultiplied 回除 `(fg.r*fg.a + bg.r*bg.a*(1-fg.a)) / a`。**判据：`fg`/`bg` 里出现「accent 色的字面值」而不是它的暗化合成值时，就是没合成到底**（如 `#ef4444` / `#1d9bf0` 原样出现）；⚠️ 这 bug 会让比值**既虚高又虚低**，所以**不能因为「比值看着离谱」就一律当误报**。修完必须重跑并**比对有没有冒出新失败**，以确认历史结论的口径 |

**结论落法**：像素复核必须与「计算样式 + alpha 合成」的**解析值互相印证**
（如 `0.62 × #eff6ff` ⇒ rgb(100,108,123) ⇒ 4.86:1）。两者一致才算定论；
不一致时先查尺子，别急着再改页面。

## 阶段 2：对比度归因（三档特异性，决定改动落点）

**先归类，再改。** 混着改会重复劳动且互相覆盖。

### 🔴 归因工具：审计只报「哪一对 fg/bg 不达标」，不说明「这条颜色是谁写的」

审计输出的选择器常常是**泛化路径**（`span.truncate.text-sm` / `span` / `div.ml-4.flex.items-center`），
拿它去 grep 源码**一定找不到**（元素很可能压根没有颜色规则，颜色是**继承**来的）。
需要一个**归因探针**，对给定选择器 dump 五样东西：

1. `classList` + `outerHTML` 片段（确认是不是内联 style / 是不是那个元素）
2. **元素级令牌值**（`getPropertyValue('--el-color-primary')` 等）⇒ 区分「变量没生效 / 生效但值不对 / 自己写死」
3. **命中该元素的全部 CSS 规则**（遍历 `document.styleSheets` 摊平，含 `@media`，只留含 `color`/`background` 的，
   用 `el.matches(sel)` 过滤）⇒ **这是找「赢家是谁」的唯一可靠办法**
4. **颜色继承链**（上溯 8 层，逐层打 `getComputedStyle().color`）⇒ 找「谁第一次把 color 变成当前值」
5. 祖先背景链（同类做法）

有了 3 + 4，上面「陷阱 5」那类「改页面组件无效」的问题**不需要猜**，一轮就能定位到主题文件的那一行。
⚠️ 遍历 `styleSheets` 时跨域表会抛异常，要 `try/catch` 跳过。

### 🔴 改前必读：CSS 特异性三档（与加载顺序无关）

| 层 | 形态 | 特异性 |
|---|---|---|
| 页面 scoped | `.a .b p[data-v-x]` | (0,3,1) —— **最高** |
| 兜底表加前缀 | `html body .ops-stat .titles p` | (0,2,3) |
| ID 限定 | `#app .x` | (0,1,1,0) |

⇒ 想覆盖页面 scoped 规则，**必须 `!important`**，否则静默失效（走过一次白干）。
另外：组件库的 `#someId button{color:inherit}`（ID 特异性）会盖掉按钮自己的 `color:#fff`；
修「深字配深底」时**必须同时补齐 `background`**，否则本来就透明底的按钮会隐形。

### 🔴 两个特异性陷阱（都让我引入过回归，务必先看）

**陷阱 1：改组件库的「实心」变体，必须加 `:not()` 修饰守卫。**
组件库的浅底变体是**两类组合选择器**，它比你的单类前缀规则**低**：

| 选择器 | 特异性 | 谁赢 |
|---|---|---|
| EP `.el-button--danger.is-plain` | (0,2,0) | — |
| 兜底层 `html.is-mobile .el-button--danger` | **(0,2,1)** | **兜底层赢** |

⇒ 你给「实心按钮」设的 `--el-button-bg-color` 会**顺手把浅底按钮的底色也刷深**，
而浅底按钮的文字色往往被同文件的另一个规则指向同一深色 ⇒ **前景 = 背景 = 同色，ratio 1.0，文字不可见**。
**修法**：`:not(.is-plain):not(.is-text):not(.is-link)`。
**判据**：复验里出现 `fg == bg`（ratio≈1.0）**几乎一定是选择器盖错，不是配色问题**，先查特异性。
**连带**：同一个文件里其它语义色（success / warning）**大概率带同一潜伏缺陷**，只是恰好没有对应变体被渲染到 ⇒ 审计看不见 ⇒ 要主动检查、一并加守卫。

**陷阱 2：给已上线的兜底层「加条件」时，用 `:where()` 锚住特异性。**
`html.is-mobile` = (0,1,1)；`html.is-mobile:not([data-theme='dark'])` = **(0,2,1)** —— `:not()` 的权重**会计入**。
多出的一档会**改变该层在全站所有优先级关系**（最典型：反过来赢过组件库更具体的还原规则，
把原本正确的颜色改坏）。**正解**：`html:where(.is-mobile):not([data-theme='dark'])`
（`:where()` 权重恒为 0）⇒ 特异性**与改动前逐位相同**，只多了匹配条件。
**判据**：任何「给既有选择器加条件」的改动，先逐位比一遍改动前后的特异性。

**陷阱 3：`!important` 写在自定义属性的**值**上时，优先于特异性。**
主题文件里常见 `--el-text-color-regular: #a3aeb9 !important;`（组件库靠它压住默认值）。
此时你写更高特异性的选择器去改**同一个自定义属性**，**照样输** —— 因为 `!important` 的声明在层叠里先于特异性比较。
（实测：`dark.scss` 给两个文本令牌写了 `!important`，我用 (0,2,1) 的选择器改，35+26 处**纹丝不动**。）
**修法**：自己的声明也加 `!important`（两边都 `!important` 时才回到特异性比较）。
**判据**：改任何深色/主题令牌前，先 `grep -n '!important' <主题文件>`，确认目标属性有没有被 `!important` 锁定。

**陷阱 4：Tailwind `dark:xxx` 是独立类名，不是「加了前缀的原类」。**
元素上是 `class="... dark:text-slate-500"`，**并没有** `text-slate-500` ⇒ 只改 `.text-slate-500` 无效，
必须写 `[class~='dark:text-slate-500']`（属性选择器比在 SCSS 里转义 `:` 和 `/` 更稳）。
**另一半是「无效类静默不生成」**：`tailwind.config.js` 的 `colors.primary` 只有
`DEFAULT/light-3/5/7/8/9/dark-2` ⇒ `dark:text-primary-300` **根本不产出 CSS**，源码里写了也白写，
元素最终继承父级颜色（实测 20 处主色链接全踩这个）。
**修法**：主色作**文字色**时不要依赖 `text-primary-NNN`，改走专门令牌
（如 `.text-primary { color: var(--xxx-primary-strong) }`），并在主题文件里为**浅/深两套**各给一个档位。

**陷阱 5：主题文件「拿别人的品牌色硬编码」时，会以更高特异性盖过页面自己的规则 ⇒ 改页面组件是白干。**
典型：项目主题文件里写
`[data-theme='dark'] .el-tree .el-tree-node.is-current > .el-tree-node__content { background: rgba(29,155,240,.1); color: #1d9bf0 }`
（`#1d9bf0` 是 CSS 框架/设计系统的品牌主色，不是本项目的 `--el-color-primary`）。
它 = **(0,5,0)**，而页面组件自己的
`:deep(.el-tree-node.is-current > .el-tree-node__content){ color: var(--el-color-primary) }` = **(0,4,0)**
⇒ **主题文件赢**，你改页面组件毫无效果，且**在页面里怎么加 `!important` 都显得莫名其妙**。
**判据**：一个元素改完页面组件却不生效时，**先 dump「命中该元素的全部 CSS 规则」**，
看赢的是不是主题文件里一条你没见过的规则（而不是继续加特异性）。
**修法**：在全局兜底层里用 (0,5,1) 之类压过它，并**在注释里写明「这条不是组件库的锅，是主题文件的品牌色硬编码」**，
否则下一个人会去改页面组件。
⚠️ 由此引出一条**分类修正**：下文的「修不动两类」里，「页面写死了 primary」要扩成
**「色被写死在 ≥ 页面 scoped 特异性的地方」** —— 可能是页面、也可能是主题文件；
后者其实**很好修**（一处全局规则 vs 逐个页面），别误归为「收益小、不值得」。

**亮/深主题互不污染**：兜底层若只针对浅色取值（深墨字压浅底），必须加 `:not([data-theme='dark'])`（或
`:where()` 版本）。否则同一批深墨色会落到深色底上，实测会出现 `rgba(15,23,42)` on `#1a2531` = **1.11:1**
的「近不可见」组 —— 比不改更糟。**深色主题自身的欠账要单独一轮**，别指望打开浅色层能顺手解决。

### 🔴 深色主题那一轮要单独做的 6 件事（做完浅色别以为收工）

1. **注入要三管齐下**：`[data-theme='dark']` + `html/body.dark` + `colorScheme='dark'`。
   只复现 CSS 层；`v-if="themeConfig.isDark"` 的 JS 分支不翻转 ⇒ 某些只在深色下渲染的内容不会出现，属已知盲区。
2. **`transition: color` 要等足**（见上表 R1，1500ms）。
3. **`/ops/*` 之类被主题锁定的页面要 `EXCLUDE`**：有 `ops-theme-lock.css` 把 ops 页锁成蓝白 ⇒ 深色审计带上它们纯属噪声。
4. **给「主色作文字色」单独造令牌**（`--xxx-primary-strong`），浅/深各一档；
   **不要改基色 `--el-color-primary`** —— 白字压主色底的按钮会从 5.9:1 掉到 2.0:1（捡了文字丢了按钮）。
5. **组件库语义基色不随主题变深**（`#67c23a/#e6a23c/#f56c6c` 深浅两套主题里是同一套）
   ⇒ 浅色层里「实心按钮底色下沉」的方案，**在深色层必须原样重放**（否则白字打回原厂高亮色，掉到 2~3:1）。
   ⚠️ 若给浅色层加了 `:where(...):not([data-theme='dark'])` 守卫，深色那半要用
   `html:where(...)[data-theme='dark']` 重新补一遍，**守卫不会自动补另一半**。
6. **浅底 plain 按钮在深色下会「白字压浅粉」—— 比实心按钮更隐蔽，必须单独重放一次文字色。**
   机理是两层叠加，缺一层都不成：
   - 主题文件给一组语义按钮写 `--el-button-text-color: #ffffff !important;`
     （如 `.el-button--primary, --info, --danger, --success, --warning` 一起）；
   - 而组件库的 `.el-button--<type>.is-plain` 设的是 `--el-button-text-color: var(--el-color-<type>)`，
     底则是 `--el-color-<type>-light-9`（**构建期 mix() 字面量，不随主题变，永远是极浅色**）。
   按陷阱 3，那条 `!important` **压过** plain 的文字色 ⇒ 拿到白字、底色仍是浅色 ⇒
   实测 `#ffffff on #fef0f0 = 1.11`（另一处 `#fee2e2 on #ef4444 = 3.08`）。
   **修法**：把浅色层里「plain 文字色」那一节**在深色层逐字重放一遍**（取值不用改，因为底没变），
   只有 `--el-button-text-color` 带 `!important` 才能抗衡主题文件的 `!important`；hover/active 底色一并下沉。
   **连带检查**：success / warning / info 的 plain **每次都漏**（这轮只有 danger 被渲染出来，
   另三个是同一潜伏缺陷）⇒ 四类一起补。
   ⚠️ `primary` 通常**不在**这一批：主题文件往往把 `--el-color-primary-light-9` 映射成了深色悬停色，
   plain 的底本来就是深的，白字反而达标。**逐个类型核对，别一刀切。**

**深色残留的两类「修不动」，别硬上全局 `!important`**：① 页面把 primary 色**写死在行内 style 或 id 选择器**里
（全局令牌够不着）；② 某个第三方组件**自己没做深色化**（如树的图标块仍是白底）⇒ 那是上游的事。
把这两类挑出来单列，收益 20 来处而回归风险陡增，不值得。**先按杠杆修**（令牌层一处能消几百处），
再收尾，顺序反了会白干。

**「映射基色」什么时候是安全的**：组件库的 `--el-color-x-light-N` 是**构建期 mix() 出来的字面量**，
改 `--el-color-x` **不会连带改变**它们 ⇒ 映射基色 ≈ 定点下沉，安全。
但**只补实测不达标的那个语义色**：整段照抄主题文件的映射可能把其它端已修好的值拖回去
（我遇到的 `--pc-good` 白底 3.75:1、`--pc-warn` 2.59:1 **本身就不达标**，另两端是靠各自的兜底层逐类覆盖才过关的）。

### 三层修复落点（按性价比排序）

1. **令牌层（收益最大）** —— 主题文件里的文字色 token alpha 偏低（如 `.58` / `.38`），
   会经 `--el-text-color-secondary` / `--el-text-color-placeholder` 扩散到全站。
   先查这里，一处改动消掉几十页。
2. **组件层** —— 「浅底 + 基色文字」的语义组件（tag / alert.is-light / 浮层 message /
   文字型按钮 `.is-link` `.is-text`）。
   ⚠️ **不改基色 `--el-color-*`**：它同时用于图表线条、边框、实心按钮，整体调深会改变视觉识别。
   定点下沉文字色，**保留边框与图标原鲜亮色**（类型识别的视觉线索）。
   ⚠️ 查主题文件有没有**直接抄组件库原厂调色板**的段落（我遇到的 `.el-message` 就是），
   那类段落既与项目主题不一致、又全部不达标。
3. **工具类层** —— Tailwind 灰字、`text-xxx/NN` 不透明度阶梯。
   抬整条阶梯时要**保持单调**（数字大的更深），并与全量色之间留层级差；
   带 `dark:` 变体的必须加 `body:not(.dark)`（或等价）守卫。

### 覆盖面清单（漏一个就要再跑一轮）

- 组件：tag · alert.is-light · **message 浮层** · button 的 `is-plain/is-text/is-link`（含各语义类型）· tree 选中态
  ⚠️ **实心变体（`:not(.is-plain):not(.is-text):not(.is-link)`）与浅底变体要成对写**，见上文「陷阱 1」。
- 页面自建状态类：`.value` / `.metric-value` / `.kpi-value` × `.ok` / `.warn` / **`.warning`** / `.danger`
  （**两种拼法都要覆盖** —— 我第一次只写了 `.warn`，复验才发现某页用全拼 `.warning`）
- 工具类：`text-gray-*` / `text-slate-*` / `text-base-content/NN` / `text-[var(--token)]`
- 计数徽标：状态 tab / 筛选按钮上的 `.count`（常见 `opacity: .75` 压暗，会把 4.5:1 压到 4.47:1）——
  **注意选中态**：蓝底白字再叠一次 opacity 会掉到 3.6:1，要单独覆盖 `.is-active`

### 🔴 Canvas 盲区：echarts / chart.js 的文字色

图表标签画进 `<canvas>`，**不是 DOM 文本节点** ⇒ `getComputedStyle` 完全看不到，
静态 grep 源码也只能证明「文件改了」，证明不了「页面上真的画出这个色」。

**做法**：在页面脚本执行前钩住绘制 API，记录每次绘制时的真实颜色与字号：

```js
await page.addInitScript(() => {
  window.__canvasText = [];
  const orig = HTMLCanvasElement.prototype.getContext;
  HTMLCanvasElement.prototype.getContext = function (type, ...rest) {
    const ctx = orig.call(this, type, ...rest);
    if (ctx && type === '2d' && !ctx.__hooked) {
      ctx.__hooked = true;
      const f = ctx.fillText.bind(ctx);
      ctx.fillText = function (t, x, y, ...a) {
        window.__canvasText.push({ text: String(t).slice(0, 30), color: String(ctx.fillStyle), font: ctx.font });
        return f(t, x, y, ...a);
      };
    }
    return ctx;
  };
});
```

比读 `echarts.getInstanceByDom(...).getOption()` 更稳：**不依赖 `window.echarts` 是否暴露**，
也不依赖 option 结构，拿到的是上屏真值。

⚠️ 已知无害噪声：echarts 会画一些 `#ffffff` 的**遮罩/底色**文字（实测某环形图中心数字
同时出现 `#ffffff` 与 `#333333` 两次绘制，`#ffffff` 那次不是可见文字）⇒ 别把这类直接当真缺陷，
先看截图确认哪一次是可见的。


## 阶段 3：渲染数据异常（顺手一起收）

- **后端计数经 JSON 回来常常是字符串**：`{"total":"0"}` 里 `"0"` 是 **truthy**
  ⇒ `!total` 的除零保护失效 ⇒ `0/"0"` = **NaN** ⇒ 页面渲染「NaN%」。
  凡后端计数一律 `Number(x) || 0`。⚠️ **`Number(x)` 只保证"是数字类型"，不保证不是 NaN**
  （`Number(undefined) === NaN`）；而 `res?.data ?? {totalCalls:0}` 在"`res.data` 是对象但缺该字段"时
  **不兜底**（`??` 只挡 null/undefined 本身）⇒ 组件把 `NaN` 直接渲染到页面上。
  **赋值处**收口（`Number(res?.data?.totalCalls) || 0`），别只在显示处包一层。
- 懒加载详情页 `onMounted` 缺空值守卫 ⇒ 路由参数缺失时仍发请求 ⇒ 404 + JS 报错。

## 阶段 4：复验与报告

1. **rebuild + 复跑同一脚本**（同一把尺子）。至少跑两轮：第一轮会暴露第一轮漏掉的覆盖面。
   🔴 **before / after 必须落成两个不同的结果文件**。若探针是「追加 + 同 path 去重取最后一条」
   （很常见，为了支持断点续跑），那么**跨修复状态重跑同一份输出文件 = 混合文件**，
   每一页可能来自不同修复时点 ⇒ **整份数据不可用于 before/after 归因**。
   做法：动手前 `cp <out> <out>.before`，修复后写到 `<out>.after` / 单独目录。
   **自检**：看记录里的时间戳范围 —— 若跨了多轮，就是混录，弃用重跑。
2. **线上实测复核**：不只看构建产物，用 Playwright 读**真实计算样式**并自己算比值。
   注意：`getComputedStyle` 返回 `rgb(r g b / a)`，**朴素正则解析会吞掉 alpha**
   ⇒ 半透明文字必须按 alpha 与背景**合成**后再算比值。
3. 🔴 **构建路线变了就必须重跑探针，别假定等价。** 容器内 `npm ci`/`pnpm` 装的依赖树 ≠ 宿主机 `node_modules`
   ⇒ **出的 dist 不是同一份产物**。同一份源码走两条路构建，行为「应该」一致 —— 但这是**要证明的结论，不是前提**。
   做法：换路线后**新开一个 tag 再跑一轮**，与上一轮逐项比对；并留一个**产物对数基线**
   （如容器 `/data/assets` 直属条目数 N，本次为 1627 / 1642）便于快速判断有没有缺块。
4. **报告必须写清三件事**，否则不算完成：
   - 修复前后**逐指标对照**（口径写明是"命中页面数"还是"元素数"）
   - **豁免项**（禁用态）单独一张表 + 为什么不能改
   - **校准为误报的清单** + 判据（让人能反驳你）
5. 若某指标是"新口径"（比如禁用态拆分后才有），基线里没有 ⇒ 标 `n/a`，**别编造 before 数字**。

## 反模式

- ❌ 不建基线就改 —— 无法证明收益，也无法证明没回归
- ❌ 改基色 `--el-color-*` 图省事 —— 图表/边框/实心按钮全被带偏
- ❌ 把禁用态当缺陷修深 —— 让禁用态看起来可点
- ❌ 无 `!important` 去覆盖页面 scoped 样式 —— 静默失效
- ❌ 只跑一轮就宣布完成 —— 第一轮必有漏网覆盖面
- ❌ 只 grep 构建产物就宣布修好 —— 半透明/渐变场景会骗过 grep，要看真实计算样式
- ❌ **只跑静态态就宣布全站覆盖** —— 弹层/抽屉/展开态整块漏检，必须补 `--click` 一轮
- ❌ **拿一份「混录」的探针结果做 before/after 归因** —— 先查时间戳范围，跨轮即弃用
- ❌ **把「没修」说成「修不了」** —— 残留项要分类：库内部绘制产物（有叶子级证据）/ 数据驱动不稳定 / 真缺陷，三者结论完全不同
- ❌ **拿 `scrollWidth` 当文本宽度** —— 块级元素不换行时它恒等于 `clientWidth`，只会给你「达标」的假象
- ❌ **半透明文字不合成就算比值** —— 3.91:1 能报成 16.62:1，修不修都会被这个数骗到
- ❌ **把「容器裁掉」当「单元格装不下」修** —— 加列宽改完截图一模一样，白干一轮
- ❌ **只看一个视口就断言布局问题** —— 宽表在 1920 放得下、在 1600 要滚动，结论会反转
- ❌ **把「采不到样（no-sample）」当成「不合格」** —— 那是在内部滚动容器里，要换元素级截图补测
- ❌ **把非文本图形（折线色/进度条）按 4.5:1 要求去改** —— 口径是 3:1，改深反而丢失类型识别色
- ❌ **换了构建路线却沿用上一轮的复验结论** —— 另一种打包方式出的 dist 是**另一份产物**，必须重跑探针
- ❌ **把基础镜像拉取超时当成"源挂了"** —— 可能只是极慢（实测 4h38m 才拉完）⇒ 长拉挂后台，别据此改构建架构
- ❌ **在 A 端达标就给 B 端盖章** —— 同源不等于同观感：入口 import、宿主路由、甚至同名路由的实现都可能不同
- ❌ **用"同名文件/文件大小/修改时间"判断两端是同一个页面** —— 一律用 `git log` 比**提交**
- ❌ **改完全站共用样式只跑业务那一组路由** —— 全局改动必须补一轮跨模块回归抽样
- ❌ **复验仍不合格就继续改页面** —— 先验证尺子（十六进制色解析 / 极小元素取样），可能是工具在骗你
- ❌ **把某端"零失败"当作"已达标"** —— 也可能是该端根本没渲染出内容（零覆盖）
- ❌ **深色注入后只等几百毫秒就采样** —— 采到的是 `transition` 过渡中间色，虚增缺陷且每轮不可比（等 1500ms）
- ❌ **用更高特异性去盖被 `!important` 锁定的自定义属性** —— `!important` 先于特异性比较，要赢就得也加 `!important`
- ❌ **以为改 `.text-slate-500` 能覆盖 `dark:text-slate-500`** —— 后者是**独立类名**，要写 `[class~='dark:text-slate-500']`
- ❌ **主色作文字色时依赖 `text-primary-300` 之类的 Tailwind 档位** —— 配置里没定义的档位**不生成 CSS**，静默失效，要用专门令牌
- ❌ **深色下给「浅色层已下沉的实心按钮」不重放底色方案** —— 组件库语义基色不随主题变深，白字会打回原厂高亮色
- ❌ **样式里对方块底写死 `#fafafa` 之类的浅色字面量** —— 文字走令牌（深色变浅）而底不变（仍白）⇒ 深色下 1.27:1 近乎不可见；底也要走令牌
- ❌ **给深色残留硬上全局 `!important` 兜底** —— 病根多半是「页面写死了色 / 组件没做深色化」，全局兜底收益小、回归风险大
- ❌ **元素改完页面组件却不生效就继续加特异性** —— 先 dump「命中该元素的全部规则」，赢家很可能是**主题文件**里一条你没见过的品牌色硬编码；加特异性等于在错的地方使劲
- ❌ **背景取底时把「半透明 ⊕ 半透明」当成不透明** —— 合成函数不回填累积 alpha 会让取底循环提前退出，**既报假失败又漏报真缺陷**（同一 bug 双向出错）
- ❌ **因为「比值太离谱」就把一条缺陷当误报删掉** —— 先确认尺子的 alpha 合成对不对；离谱可能是尺子坏了，也可能是坏得不对称
- ❌ **深色下只重放「实心按钮底色」却忘了「浅底 plain 按钮文字色」** —— 主题文件的 `#ffffff !important` 会压过组件库的 plain 文字色，于是白字配浅底（1.11:1）
