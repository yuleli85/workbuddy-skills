# 数字员工角色字典

组队时为每个子任务匹配角色。原则：**任务需要什么专业能力就派谁**，字典覆盖不到的领域用领域 skill，不硬造角色。

## 通用工程角色

| 角色 | 代号（spawn 名） | 职责 | 产出物 | 何时派 | model 建议 |
|---|---|---|---|---|---|
| 需求分析员 | `product-analyst` | 目标澄清、验收标准细化、任务边界划分、假设与风险识别 | 需求/任务清单文档 | 目标模糊、验收标准不明、多干系人口径需统一时第一个上场 | reasoning |
| 架构师 | `architect` | 方案设计、技术选型权衡、接口契约、模块划分 | 方案文档 + 接口契约 | 非平凡特性（新技术引入、跨模块改动、数据流设计）动手前 | reasoning |
| 前端工程师 | `fe-dev` | 页面/组件/交互/样式，走真实浏览器验证 | 代码 + 可运行页面/截图 | 有 UI 产出的任务 | default |
| 后端工程师 | `be-dev` | Java/接口/SQL/业务规则/权限/事务 | 代码 + 测试通过的证明 | 服务端逻辑、数据库、API | default |
| Python/AI 工程师 | `py-dev` | FastAPI/数据管线/模型适配/脚本 | 代码 + 运行输出 | Python 侧、AI 链路、数据处理 | default |
| 测试工程师 | `qa` | 用例设计、执行验收、缺陷定位（只报不改） | 验收报告 + 缺陷清单 | **每次质量门必派**；多人并行开发时可提前介入写用例 | default |
| 文档工程师 | `doc-writer` | 交付文档、README、汇报材料、通俗化改写 | 结构化文档 | 交付物含文档/报告/PPT 时 | default |
| 项目助手 | `pm` | 进度汇总、风险清单、跨任务协调信息整理 | 状态汇总/日报 | 任务 ≥6 个或跨多角色时派，做编排者的秘书 | lite |

## 特殊领域：不造角色，挂领域 skill

角色字典只覆盖通用工程角色。子任务属于下列领域时，在员工 prompt 中直接指定加载对应 skill（员工自己执行）：

| 领域 | skill | 说明 |
|---|---|---|
| 金融/投资/行情 | `wb-finance-skill`、`westock-data` | 优先于通用角色 |
| PPT 产出 | `zh-ppt` 或 `tencent-pptx` | 交付物是演示文稿时 |
| Word 文档 | `tencent-docx` | 研报/合同/公文类 |
| Excel | `tencent-docs-sheet-generation`（新建）/ `tencent-docs-sheetagent`（处理既有表） | |
| 视频 | `make-video` | 配音/成片 |
| 浏览器验收 | `pig-ui-browser-verify`（灵猫项目）/ `agent-browser` | UI 真机验证 |
| 代码审计 | `code-audit` | 安全/交付质量审查 |

## 派单判据（选人速查）

- 目标说不清 → 先 `product-analyst`，再谈开发。
- 要写代码 → `architect`（若非平凡）→ `fe-dev`/`be-dev`/`py-dev` 按技术栈。
- 要改既有代码且行为不明 → 先派一个 Explore 探查任务（可用 general-purpose/Explore agent），把调用链摸清写进产物目录，再派开发。
- 谁都可以做的小事（查资料、跑脚本、汇总数据）→ 主编排者自己做或派 `pm`，不占专业编制。
- **`qa` 永远不做实现**（既当运动员又当裁判是质量门失效的第一大原因）；开发员工也永远不给自己的产物签验收。

## 编制规模参考

| 任务规模 | 建议编制 |
|---|---|
| ≤3 个子任务 | 主编排者直接做 + qa 验收，最多加 1 名开发 |
| 4~6 个子任务 | 1~2 名开发 + qa（+ architect 若非平凡） |
| ≥7 个子任务或跨 3+ 专业 | 全编制：product-analyst → architect → 2~3 开发并行 → qa → doc-writer（+pm） |
