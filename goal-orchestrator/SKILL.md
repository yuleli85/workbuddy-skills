# Goal Orchestrator — 数字员工团队编排器

## 概述

把「一句目标」变成「一支分工明确、互相协同、有质量门的数字员工团队」，直到交付并可说明下一步。主编排者（本会话）是唯一的指挥与裁决者；数字员工是通过 Agent 工具生成的子代理，每个员工专注一个专业角色。

**核心纪律（全程有效）**：

- 主编排者不亲自写实现，只做：拆解、派单、整合、裁决、验收抽查、交付。
- **Trust but verify**：员工汇报"完成"不等于完成。验收以产物文件为准（读文件、跑测试、看输出），不以员工的自述为准。
- 每个子任务必须有**可观察的验收标准**（能跑的命令、能读的产物、能对上的数字），没有验收标准的任务不派单。
- 员工 prompt 必须自包含：目标背景、任务边界、验收标准、项目规则摘要、产物落点路径。子代理看不到本会话上下文。

## 第 0 步 · 适用判断（先判断，别过度编排）

满足任一条**才组队**，否则直接执行并说明"任务简单，未组队"：

- 需要 ≥3 个不同专业角色的产出（如 需求→开发→测试→文档）；
- 产物是多个文件 / 多模块的系统性改动；
- 任务之间有依赖链或需要并行加速。

组队后仍保持轻量：角色按需上，不为了"像团队"而凑满编制。3 个角色能做完的事不派 6 个。

## 第 1 步 · 目标解析

1. 复述目标，判定类型：功能开发 / 文档报告 / 数据分析 / 内容创作 / 调研决策 / 修复问题。
2. 收集项目上下文（并行读）：项目 `AGENTS.md`、`.workbuddy/memory/MEMORY.md`、最新日报；若项目有 `数字员工/` 目录约定（读最近一份日报了解格式），沿用它。
3. 写出**总验收标准清单**：可观察、可验证、逐条可勾选。
4. 信息不足时做合理假设并显式标注"假设"，不反问卡死；只有 🔴 不可逆操作（删数据、对外发送、改生产）才必须先问用户。
5. 产出作战计划（模板见 `references/templates.md` §1）：目标 → 假设 → 任务分解表（任务/角色/依赖/验收）→ 产物目录。用一段简短文字向用户展示后**立即开工**，不等确认（除非含 🔴 操作）。

产物目录统一为：`<workspace>/output/task-list/<目标短名>/`，所有中间产物与交付物落这里。

## 第 2 步 · 任务拆解与登记

- 用任务管理工具（TaskCreate）建任务清单，每个任务字段：subject（祈使句）、description（含验收标准 + 产物路径）、owner（角色代号）。
- 用 addBlockedBy 登记依赖；无依赖的任务并行。
- 粒度标准：**一个任务 = 一个员工一次执行可完成**。超过就继续拆；拆不动的超大任务先派 architect 出方案再拆。
- 任务状态实时维护：开工前 in_progress、真正完成后才 completed（产物验收通过才算完成，员工自述不算）。

## 第 3 步 · 组队与派单

- 从 `references/roles.md` 的角色字典为每个任务匹配最优员工；字典覆盖不到的专业领域（金融、视频、PPT、爬虫等）不硬造角色，改用对应领域 skill 或让员工在 prompt 里挂载该 skill。
- 用 Agent 工具 spawn 员工，一个员工名 = 一个角色代号（如 `product-analyst`、`fe-dev`、`qa`）。
- spawn prompt 骨架（完整模板见 `references/templates.md` §2）：身份与职责 → 目标与背景 → 本任务边界与验收标准 → 项目硬规则摘要（从 AGENTS.md 提炼，特别是红线）→ 产物落点 → 汇报格式要求。
- 可并行的任务在**同一条消息里并行 spawn**（多个 Agent 调用一次发出）。
- 员工执行用 TaskUpdate 同步状态；需要中途补充信息时用 SendMessage 找该员工，不重新 spawn。

## 第 4 步 · 协同

- 上游产物 → 下游消费：一律通过共享产物目录交接（文件是真源），下游员工的 prompt 里写明要读哪些上游文件。
- 员工完成后的标准汇报四件套：做了什么 / 产物路径 / 自检结果（跑了什么验证）/ 遗留问题。
- 冲突由主编排者裁决（如两个员工对同一文件给出不同改法），裁决依据是总验收标准与项目规则，不是员工资历。
- 员工之间不直接互相改对方的产物文件；需要改时回报主编排者重新派单，避免并发覆盖。

## 第 5 步 · 质量门（"做到完美"的可执行定义）

1. 所有实现类任务完成后，派 **qa** 员工做交叉验收：对照每个任务的验收标准逐条核（代码真跑测试、文档真读内容核对、页面真打开验证），输出验收报告（通过/不通过 + 缺陷清单）。
2. 不通过的任务**打回原员工重做**：打回单必须附具体缺陷（哪条验收标准、什么现象、期望 vs 实际），禁止"再优化一下"式模糊指令。
3. **重试上限 2 轮**：2 轮后仍不通过 → 停止迭代，如实把剩余缺陷写进交付报告的"已知风险"，不假装完美。
4. 主编排者亲自抽查关键产物至少 1 项（读文件/跑命令验证），qa 的报告也要被抽查——验收者本身不可豁免。

## 第 6 步 · 交付

1. 用 present_files 一次性交付全部产物（报告放第一位）。
2. 交付报告按 `references/templates.md` §3 的 L0~L3 结构写进 `<产物目录>/交付报告.md`：
   - L0 结论（一句话：目标是否达成 + 完成度）；
   - L1 任务完成表（任务/员工/验收结果/产物路径）；
   - L2 文件清单与使用方式（怎么跑、怎么看）；
   - L3 已知风险与遗留问题（如实，含质量门未通过项）。
3. **「下一步需要你做什么」三档清单**（模板见 §4）：
   - 🔴 必须决策：阻塞项，不决定就无法继续的事（含选项和我的建议）；
   - 🟡 建议验收：给我做的成果做人工复核的具体动作（看哪、跑哪条命令）；
   - ⚪ 可选优化：不阻塞但做了更好，建议下期处理。
4. 记忆收尾：有 `.workbuddy/memory/` 的项目追加当日日报；有 `数字员工/<角色>/` 约定的项目，按其既有日报格式为每位员工留档一份（格式参考 `references/templates.md` §5）。

## 红线（违反任何一条即流程失败）

- 不允许把员工自述当验收结果；必须有产物级证据。
- 不允许无验收标准的任务进入派单。
- 不允许员工 prompt 里出现"参考我们之前的对话"这类依赖会话上下文的写法。
- 不允许为凑满团队编制而派闲职员工。
- 质量门不允许 0 轮就交付（哪怕任务再简单，qa 至少核一遍），也不允许超过 2 轮打回后仍宣称"完美"。
- 涉及 🔴 不可逆/对外操作（发消息、发邮件、删数据、改生产库、git push 共享分支）必须先经用户确认，任何员工不得自行执行。
